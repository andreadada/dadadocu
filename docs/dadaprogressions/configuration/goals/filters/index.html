Filters

Filters decide whether a matching event is allowed to add progress. They do not change the amount; use point rules for that.

Every goal may have its own filters. On a simple goal they apply to its single event criterion. On a composite goal, top-level filters apply to every event leaf, and a leaf may add more local filters.

Standard syntax​

filters:
  entity-type:
    include: [ZOMBIE, SKELETON]
  world:
    include: [survival, survival_nether]
KeyTypeMeaning
includeString or string listAccept any listed value. Missing or empty means every value that is not excluded.
excludeString or string listReject any listed value. Exclusion always wins over inclusion.

By default, different filter modules are combined with AND. In the example, the entity must be a zombie or skeleton and the event must happen in one of the two worlds.

Values inside one include list are combined with OR.

ALL or ANY​

Use filter-mode next to filters to control how different modules are combined:

filter-mode: ALL
filters:
  world:
    include: [survival]
  game-mode:
    include: [SURVIVAL]
ValueMeaning
ALLEvery configured filter must match. This is the default and preserves existing behavior.
ANYAt least one configured filter must match.

Example: allow progress in the mines world or allow a VIP player anywhere:

filter-mode: ANY
filters:
  world:
    include: [mines]
  permission:
    include: [server.vip]

An empty filter list always passes, even with ANY. Global and criterion-local filters remain separate stages: the goal's global stage must pass, then the leaf's local stage must pass.

Short syntax​

When you only need include, a scalar or list is accepted:

filters:
  material: DIAMOND_ORE
  world: [survival, mines]

The expanded form is easier to extend later and is recommended for public configurations.

Filter keys may also use underscores (entity_type), but they are normalized to hyphens. The documented hyphen form is preferred.

Material​

material describes the block or item involved in the event, not an arbitrary item in the player's inventory.

filters:
  material:
    include: [DIAMOND_ORE, EMERALD_ORE]
    exclude: [STONE]

Material names depend on the Minecraft/Bukkit version. A name that exists on a modern server may be invalid on an old server. Invalid names fail goal validation instead of being silently ignored.

For ITEM_CRAFT, the material is the recipe result. For ITEM_SMELT, it is the extracted result. For ANIMAL_BREED, it is the breeding item when the server event exposes it.

Entity type​

filters:
  entity-type:
    include: [ZOMBIE, HUSK, DROWNED]

Entity names are Bukkit EntityType values. They are version-dependent. On PLAYER_KILL the entity type is PLAYER; on damage goals it is the entity receiving the damage.

World​

filters:
  world:
    include: [survival, survival_nether]

Use the real world name from the server, not the display name of a world-management plugin. Comparison is case-insensitive, but the name must otherwise match.

For single-valued filters such as world, choose one of these common forms:

# Only these worlds
world:
  include: [survival, survival_nether]
# Every world except lobby
world:
  exclude: [lobby]

Using include: [survival] together with exclude: [lobby] is valid but redundant: lobby is already outside the include list.

Game mode​

filters:
  game-mode:
    include: [SURVIVAL, ADVENTURE]
    exclude: [CREATIVE, SPECTATOR]

The value is the actor's game mode when the event is processed.

Permission​

filters:
  permission:
    include: [server.progressions]
    exclude: [server.progressions.disabled]

When include contains several permissions, having any one of them is enough. If the player has any excluded permission, the event is rejected even when an included permission is present.

Command​

type: COMMAND_RUN
filters:
  command:
    include: [spawn, warp]

Use only the first command word. /warp mines becomes warp; arguments are not available to this filter.

Damage cause​

type: DAMAGE_TAKEN
filters:
  damage-cause:
    include: [FALL, FIRE, LAVA]

Damage-cause names come from Bukkit and can vary by server version. Invalid values fail validation.

Attribution​

type: ANIMAL_BREED
filters:
  attribution:
    include: [EXACT]
ValueMeaning
EXACTThe server event directly identified the breeder.
INFERREDOn legacy servers, DadaProgressions inferred the player from a recent interaction near the bred animal.

Use EXACT when rewards must only be granted from direct attribution. Omit the filter to accept both modes.

Biome​

filters:
  biome:
    include: [PLAINS, FOREST]

Biome names come from Bukkit and depend on the server version. Block events use the block location; kill, damage, and breeding events use the involved entity location; other player events use the actor's current location.

Height bounds​

Numeric bound filters use a single scalar value and do not support exclude:

filters:
  min-y: 0
  max-y: 64

Both filters use ALL by default, producing an inclusive range from Y 0 through Y 64.

Event-amount bounds​

filters:
  min-amount: 10
  max-amount: 64

The value is the event's amount before point rules. For pickup, drop, and smelt events it is normally the stack/extracted amount. For damage it is rounded final damage. Most other automatic events have amount 1.

Global and local filters​

goals:
  weekly_tasks:
    filters:
      world:
        include: [survival]
    criteria:
      operator: AND
      children:
        mining:
          type: BLOCK_BREAK
          target: 100
          filters:
            material:
              include: [STONE, DEEPSLATE]
        hunting:
          type: MOB_KILL
          target: 20
          filters:
            entity-type:
              include: [ZOMBIE]

The global world filter must be compatible with every leaf. Local filters only need to be compatible with their own leaf type.

Common mistakes​

  • Using a filter that does not support the goal type.
  • Using plugin display names instead of Bukkit material/entity/world names.
  • Giving a numeric bound more than one value or adding exclude; numeric bounds accept exactly one scalar.
  • Expecting exclude to be ignored when the same value is also included.
  • Filtering a manual API trigger: direct API amounts do not carry an event context, so event filters are only evaluated by automatic tracking.

Debugging a real event​

Arm a one-shot debug for an online player:

/dp admin debug <goalId> <player> [timeoutSeconds]

The next automatically tracked event whose type is used by that goal prints:

  • event type and base amount;
  • enabled and prerequisite state;
  • global and criterion filter modes;
  • actual value, include list, exclude list, and pass/fail for every filter;
  • the first matching point rule, its operation and when-mode;
  • base and final points after point rules;
  • cooldown acceptance and final result.

The debug request is consumed after the first relevant event. It expires after 60 seconds by default; pass a value from 5 to 600 seconds to change that, or use /dp admin debug cancel <player>. VOTE and CUSTOM progress added directly through commands or API calls does not create an automatic event context.
