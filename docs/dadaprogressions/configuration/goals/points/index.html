Points and multipliers

Point settings transform the amount produced by a matching event. Filters decide whether an event matches; point rules decide how much progress it gives.

Key reference​

points:
  base: EVENT_AMOUNT
  rounding: FLOOR
  rules: []
KeyTypeDefaultAccepted values / purpose
baseString or integerEVENT_AMOUNTEVENT_AMOUNT uses the listener amount; a non-negative integer uses a fixed starting amount.
roundingEnumFLOORJava rounding mode used after multiplication. Common values: FLOOR, CEILING, HALF_UP.
rulesList of mapsEmptyOrdered rules. The first matching rule wins.
rules[].when-modeEnumALLALL requires every condition in this rule; ANY requires at least one.
rules[].whenFilter mapEmptyUses the same keys and values as Filters. Empty matches every event.
rules[].setNon-negative integer—Replaces the result with this exact amount. Mutually exclusive with multiply.
rules[].multiplyNon-negative decimal—Multiplies the base amount. Mutually exclusive with set.

Each rule must contain exactly one of set or multiply. Negative values are invalid. A result of zero does not add progress, trigger a cooldown, or send a progress notification.

when-mode: ALL or ANY​

when-mode belongs to one point rule and combines only the entries under that rule's when. It is separate from the goal's filter-mode.

points:
  base: 1
  rules:
    - when-mode: ALL
      when:
        material: [DIAMOND_ORE]
        world: [survival]
      set: 10

With ALL, both conditions must pass: the block must be diamond ore and the event must happen in survival.

points:
  base: 1
  rules:
    - when-mode: ANY
      when:
        material: [DIAMOND_ORE]
        world: [mines]
      set: 10

With ANY, one condition is enough: diamond ore in any allowed world or any matching block in mines receives 10 points. Use ANY deliberately; broad conditions can make a valuable rule match more events than expected.

An empty when matches every event, regardless of when-mode. Such a rule acts as a fallback and should normally be last.

Event amount versus fixed base​

points:
  base: EVENT_AMOUNT

This preserves amounts such as a picked-up stack size, extracted smelt count, or rounded damage.

points:
  base: 1

This makes every matching event start at one point, even if the listener reported a larger amount.

Fixed values with set​

type: MOB_KILL
target: 500
points:
  base: 1
  rules:
    - when:
        entity-type:
          include: [WITHER]
      set: 100
    - when:
        entity-type:
          include: [ENDERMAN]
      set: 5

A wither gives 100 points, an enderman gives 5, and every other matching mob keeps the base value of 1.

Multipliers​

type: BLOCK_BREAK
target: 1000
points:
  base: EVENT_AMOUNT
  rounding: FLOOR
  rules:
    - when:
        material:
          include: [DIAMOND_ORE]
      multiply: 10
    - when:
        material:
          include: [GOLD_ORE]
      multiply: 3.5

Multiplication uses decimal arithmetic, then applies rounding to produce whole progress points.

Rounding valueExample for 2.5
FLOOR2
CEILING3
HALF_UP3

Other valid values come from Java RoundingMode, but these three cover most goal configurations.

Rule order matters​

Only the first matching rule is used. Put narrow, valuable cases before broad cases:

rules:
  - when:
      entity-type: [WITHER]
      world: [boss_arena]
    set: 200
  - when:
      entity-type: [WITHER]
    set: 100

In boss_arena, the first rule wins. Elsewhere, the second rule can match.

The complete evaluation order is:

  1. the event must pass the goal or criterion filters using its filter-mode;
  2. point rules are read from top to bottom;
  3. each rule evaluates its own when using its own when-mode;
  4. the first matching rule applies set or multiply;
  5. if no rule matches, the configured base is used unchanged.

Visual editor​

Open /dp admin editor, select a goal and then an event criterion. The Point rules screen lets you:

  • switch the base between EVENT_AMOUNT and a fixed value;
  • cycle the rounding mode;
  • add SET and MULTIPLY rules;
  • change a rule's value and ALL/ANY mode;
  • move rules up or down, or remove them;
  • edit the when filters through private chat.

The chat syntax for conditions is:

material=DIAMOND_ORE,DEEPSLATE_DIAMOND_ORE; world=survival

Use .include or .exclude when both sides are useful:

world.include=survival,survival_nether; world.exclude=lobby

Enter none to clear all conditions or cancel to leave the rule unchanged. Every edit is validated before it replaces the active configuration.

Debugging the winning rule​

Arm a one-shot trace, then perform the relevant action with the selected player:

/dp admin debug <goalId> <onlinePlayer> [timeoutSeconds]

The report identifies the first point rule that matched, its operation and when-mode, and the base-to-final point calculation. The timeout defaults to 60 seconds and accepts 5 through 600 seconds. Cancel an unused trace with:

/dp admin debug cancel <onlinePlayer>

Composite goals​

On a composite goal, place points on each event leaf:

criteria:
  operator: AND
  children:
    mining:
      type: BLOCK_BREAK
      target: 100
      points:
        base: 1
        rules:
          - when:
              material: [DIAMOND_ORE]
            set: 10

Point-rule filters must be compatible with that leaf's type. They do not replace the goal or leaf filters; the event must pass those first.
